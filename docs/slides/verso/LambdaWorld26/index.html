What is Formal Verification?

Formal verification is the practice of stating and proving theorems about code, to show that the code conforms to a specification.

def g (n : Nat) : Id Nat := do let mut x := n x := 2 * x x := x + 1 return x -- for any input n, g n returns 2 * n + 1 theorem g_spec (n : Nat) : ⦃⌜True⌝⦄ g n ⦃⇓ r => ⌜r = 2 * n + 1⌝⦄ := byn:Nat⊢ ⦃⌜True⌝⦄ g n ⦃PostCond.noThrow fun r => ⌜r = 2 * n + 1⌝⦄ mvcgen [g]All goals completed! 🐙

Performant Lean

Performant Lean

Classic objection: functional languages are slower than imperative, low-level languages like C and Rust.

The reason: functional languages don't have the same fine-grained control over memory as low-level languages.

The new reality: if your functional language has proofs, then you can make radical, agent-led optimization passes.

The result: verified Lean code that keeps up with C and Rust, and sometimes beats them.

Lean-Zip

DEFLATE in pure Lean, proved inflate (deflate x) = x, then optimised by agents.

  • 4.57s vs 5.77s in Rust, on the 212 MB Silesia corpus

  • 30% faster than Rust at the default level

  • 2× faster than Rust at maximum compression

  • 1 proof keeps every agent optimisation honest

Beats Rust's miniz_oxide and C's reference zlib at every level. Heavily optimised C (zlib-ng, libdeflate) is still faster.

  • Rust comparisons:

    • miniz_oxide: pure Rust, the 5.77s; beaten at every level.

    • zlib-rs: still faster across most of the range.

  • Pure Lean DEFLATE; theorem: inflate (deflate x) = x for every input.

  • Demo: 212 MB Silesia, level 6: 4.57s vs Rust's 5.77s, smaller output too.

  • Chart: red is lean-zip, one frame per commit, climbing past Rust.

  • Agents did the optimizing; nothing merged unless the proof held.

  • "The proof is the ratchet."

  • Honest: zlib-ng and libdeflate still faster; more memory; slower decompression.

  • Fuzzing: 0 bugs in verified code, 1 in Lean's own runtime (fixed same day).

Gaps

The proofs held up. Here's what these projects still had to work around.

  • Low-level control. Core lacks fast packed-word access, so CompPoly backports it in C. No SIMD types.

  • Per-core speed. Hand-tuned C and Rust still win on one core.

  • A young runtime. Lean-Zip found a bug in Lean's own runtime.

  • Ecosystem. Async and HTTP just landed. No TLS, few libraries, hand-written C bindings.

  • Stability. Monthly releases, breaking changes, no LTS.

  • The honest caveat; every gap is one the case studies hit.

  • Low-level: CompPoly needs two C helpers; no SIMD.

  • Per core: Plonky3's AVX2 is 2–3× faster; Lean wins with parallelism.

  • Runtime: Lean-Zip's runtime bug, fixed fast.

  • Ecosystem: no TLS, few libraries, hand-written FFI.

  • Stability: monthly breaking releases, no LTS.

  • Line: "None of this is fundamental. It's engineering, and agents are getting good at engineering." Into Autoresearch.

Autoresearch

Autoresearch

Give an agent a cost to minimise and a proof it must keep. Then let it loop, overnight.

  • cost ↓ what the agent minimises: time, cycles, code size

  • ⊢ spec what it can never break: the proof must still check

The main idea: a proof is the clearest goal you can give an agent. It can't game the score, so the only way to win is better code that's still correct.

  • Karpathy's autoresearch (March): agent edits, measures, keeps or reverts, overnight.

  • Lean adds one gate: the proof must check before anything is measured.

  • Walk the loop: change code, Lean checks, measure cost, keep or revert.

  • Cost can be anything: time, cycles, code size, gas.

  • Unconstrained optimizers game the metric; the proof rejects every cheat.

  • So it runs unattended. Transition: the competitions are exactly this.

zk.golf

Build the smallest zero-knowledge circuit for a task, proved in Lean to match its spec.

  • 7.4× smaller secp256k1 circuit than circom-ecdsa

  • 2.6× smaller RSA check than zk-email's

  • 1.9× smaller SHA-256 than xJsnark's

A smaller circuit means a cheaper proof. And here, a smaller circuit can't be a broken one.

LLMs as Compilers

LLMs as Compilers

The usual pipeline: write high-level code, then trust the compiler to get the machine code right.

The new pipeline: give an agent a spec of the program and a spec of the machine, and have it write the machine code directly.

Lean checks the result: the code is proved against the spec, so there's no compiler left to trust.

  • A compiler is a trusted translator; here the agent translates and a proof replaces the trust.

  • You never trust the agent; Lean checks its output.

  • Ethereum: zkVM proofs don't cover rustc or LLVM. Proved assembly removes them.

  • Roadmap: evm-asm (big), xmss (small, one sitting), flapjack (the lesson at scale).

evm-asm

Agent-written RISC-V, proved against the EVM spec.

Every solid layer is a Lean theorem; checking a whole block is still being proved.

  • Bottom: the official Sail RISC-V spec, the trust anchor.

  • evm-asm's RISC-V semantics are proved equal to Sail.

  • Hoare triples with a step bound: worst-case cycles are a theorem.

  • The code is the real AND: 17 instructions over four 64-bit limbs.

  • Top: checking a whole block; tested, not yet proved (dashed).

  • History: Yoichi Hirai, Feb 2026; 96 commits in Feb, 19,126 in May.

  • Status: 68 of 85 opcodes proved; 0 sorry in the core.

Machine-Checked ✅

Skip the compiler question: prove the binary itself correct.

The binary can come from any compiler, or be optimised by hand. What's trusted: the machine model, the loaded image, and Lean's kernel.

  • Where the last slides lead: don't trust the compiler, check its output.

  • The source can be anything; the compiler isn't trusted.

  • elf2lean decodes the ELF into Lean instructions on a machine model (riscv-zkvm).

  • Prove the decoded program meets the spec.

  • Trusted base: the machine model, the loaded image, Lean's kernel.

  • Worked example: zip-2005-asm (from the Cambridge talk).

  • Open question: zkVMs differ (SP1 vs ZisK: calling conventions, memory layout, I/O).
