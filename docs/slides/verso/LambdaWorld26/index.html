What is Formal Verification?

Formal verification is the practice of stating and proving theorems about code, to show that the code conforms to a specification.

def g (n : Nat) : Id Nat := do let mut x := n x := 2 * x x := x + 1 return x -- for any input n, g n returns 2 * n + 1 theorem g_spec (n : Nat) : ⦃⌜True⌝⦄ g n ⦃⇓ r => ⌜r = 2 * n + 1⌝⦄ := byn:Nat⊢ ⦃⌜True⌝⦄ g n ⦃PostCond.noThrow fun r => ⌜r = 2 * n + 1⌝⦄ mvcgen [g]All goals completed! 🐙

Until Now ...

  • Theorem provers (like Lean) have been niche, "experts only."

  • Verification projects take months or years, with huge demands on expertise.

  • Formal verification has been selectively applied, only to the most security-critical software.

CompCert

A C compiler, proved in Coq never to miscompile.

  • 100,000 lines of Coq

  • ¾ of it is proof, not compiler

  • 6 person-years of specialist work

  • 11 years, 2005 to 2016

And the result is still niche: ~20% behind gcc -O2, with a licence for commercial use.

The first optimizing C compiler proved, in Coq, not to miscompile.

Team size: there is no published head count. The honest figure is Leroy's "six person-years" (ERTS 2016), spread over a small named core (see below).

"¾ of it is proof" is the CACM 2009 breakdown (76% proof, 14% compiler, 10% semantics), taken from the 42,000-line version.

The exhibit for the previous slide: a monumental proof, done by specialists, applied only where miscompilation is unacceptable.

Accomplishment. CompCert (Xavier Leroy, Inria, from 2005) compiles a large subset of C to assembly, with a machine-checked proof of semantic preservation: if compilation succeeds, every behavior of the assembly is a behavior allowed by the C semantics (or a defined refinement of an undefined one). The 2016 line is "the first commercially available optimizing compiler" proved exempt from miscompilation.

The demo that sells it: Yang, Chen, Eide, and Regehr, PLDI 2011, hunted wrong-code bugs with Csmith. They found them in GCC and LLVM. "CompCert is the only compiler we have tested for which Csmith cannot find wrong-code errors."

What it cost. Two published snapshots, both Leroy's:

  • CACM 2009: 42,000 lines of Coq, about three person-years. Of that, 14% is the compiler, 10% the semantics, 76% the proof.

  • ERTS 2016 (repeated in "Closing the Gap", 2017, and still the figure AbsInt quotes): 100,000 lines of Coq, six person-years.

Say "six person-years," not "a team of N for Y years." The named core is small — Leroy, Sandrine Blazy, Zaynah Dargaye, Jacques-Henri Jourdan, Michael Schmidt, Bernhard Schommer, Jean-Baptiste Tristan — and six person-years from 2005 to 2016 is well under one full-time person. No newer effort total has been published; the compiler is still maintained.

Why it stayed niche.

  • Speed: on the published benchmarks, about 10% behind gcc -O1 and about 20% behind gcc -O2, and further behind where aggressive loop optimizations matter. Fine for critical embedded code, not a GCC replacement. (AbsInt's summary: about 2× gcc -O0, ~10% behind -O1, ~20% behind -O3.)

  • License: the public sources are for evaluation, research, teaching, and personal use. Commercial use is an AbsInt license.

  • The users match that: life- and mission-critical embedded software (MTU Friedrichshafen is the published story), not ordinary C.

Scaling (Formal Verification)

Anthropic and Theorem: real C libraries, proved crash-free at the binary level, Oct 2026.

  • 123 open-source libraries proved crash-free

  • 180M lines of Rocq

  • weeks not person-years

  • 100s of bugs found along the way

For scale: seL4 took 20 person-years to verify. Meanwhile, agents verified the xv6 kernel down to the hardware in 77 days.

Sources: Anthropic Frontier Red Team, "LLMs are making formal software verification feasible at a much larger scale" (22 Oct 2026), with Theorem, plus its appendix; Kaashoek and Zeldovich, arXiv:2609.04043 (3 Sept 2026).

  • The spec is the library's own OSS-Fuzz test. For every input under 64 MB, the compiled program exits normally, with no memory-safety error (ASan) and no failed assertion.

  • Proved for 239 entry points across 123 OSS-Fuzz libraries, "over the span of a few weeks." Claude patched the bugs it found, then proved the patched code.

  • The proofs are on RISC-V executables, not source, using Theorem's RISC-V and Linux process semantics. Assumes a single-threaded static binary with a fixed memory budget.

  • About 180 million lines of Rocq passed the checker, out of about a billion written. A typical proof is ~600,000 lines in ~1,400 files, for a binary with a median of 18,000 instructions. cJSON's 391-line parser got a 630,000-line proof. Only the trusted base needs reviewing: Rocq, the RISC-V and Linux semantics, and the spec.

  • Bugs a fuzzer would never find: an out-of-bounds write needing a ~20 MB input with one rare layout, and an out-of-bounds read needing 64 MB of input and 2 GB of memory. It also rediscovered CVE-2026-56132 in libexpat. On a PDF reader, it found a year's worth of security bugs in one week.

  • In the same post: the Linux kernel's zlib proved correct against RFC 1950 on the x86 binary, and a Python interpreter in Rust proved (in Verus) to follow CPython semantics.

  • Cost: no dollar figure. Proofs "can take hundreds of millions of tokens." Opus 5.5 needs ~40% fewer tokens than Opus 5.

  • xv6: 6,593 lines of C and assembly, multicore, verified against Sail RISC-V semantics with concurrent separation logic (MachCSL, built on Iris). It found nine bugs in xv6 and one in the Sail spec. The 77 days include building the framework.

  • The seL4 figures are Anthropic's own framing in the post.

The image shows what each proof is made of: most of it is shared machinery (allocator, sanitizer runtime, libc) reused across libraries.

Performant Lean

Performant Lean

Classic objection: functional languages are slower than imperative, low-level languages like C and Rust.

The reason: functional languages don't have the same fine-grained control over memory as low-level languages.

The new reality: if your functional language has proofs, then you can make radical, agent-led optimization passes.

The result: verified Lean code that keeps up with C and Rust, and sometimes beats them.

Lean-Zip

DEFLATE in pure Lean, proved inflate (deflate x) = x, then optimised by agents.

  • 4.57s vs 5.77s in Rust, on the 212 MB Silesia corpus

  • 30% faster than Rust at the default level

  • 2× faster than Rust at maximum compression

  • 1 proof keeps every agent optimisation honest

Beats Rust's miniz_oxide and C's reference zlib at every level. Heavily optimised C (zlib-ng, libdeflate) is still faster.

Sources: Kim Morrison, "Why Lean is faster than Rust" (24 July 2026); github.com/kim-em/lean-zip and lean-zip-benchmark.

The demo: time on silesia.tar (212 MB), level 6. miniz_oxide (pure Rust, no unsafe): 68,112,144 bytes in 5.77s. lean-zip: 68,054,183 bytes in 4.57s, so smaller and faster.

The chart: further left is better compression, further up is faster (log scale). Green is miniz_oxide across its levels. Red is lean-zip, replayed one frame per commit of the project's history, June to July 2026. It starts far below everything and climbs past Rust.

Why it works: the theorem inflate (deflateRaw data level) = .ok data holds for all inputs. Essentially all the performance work was done autonomously by Claude and Codex agents, and no PR could merge unless the round-trip proof still went through. "The proof is the ratchet." You could point agents at miniz_oxide too, but you'd have to audit everything they produced.

Against the wider field (README, at matched compression ratio):

  • miniz_oxide: beaten at every level L1–L9 (one asterisk at L3). +16% at L1 with 8.8% smaller output, ~30% at L6, ~2× at L9.

  • zlib (the C reference): dominated at every level.

  • JS fflate: 1.5–2× faster; OCaml decompress: 3–9× faster.

  • Go and Zig: they win the low levels, lean-zip wins the dense end.

  • zlib-ng (C) and zlib-rs (Rust): faster across most of the range; lean-zip is level or slightly ahead at their densest setting.

  • libdeflate (hand-tuned C + SIMD): ~2× faster at mid ratios, up to ~10× at the dense end.

Honest caveats (Kim's own): higher memory use; decompression is ~1.45× slower than miniz_oxide; a few @[extern] helpers (word-sized ByteArray reads) are trusted.

The Lean bug: in April 2026 Kiran Gopinathan pointed a Claude agent with AFL++ and sanitizers at lean-zip, for 105 million executions. It found zero memory bugs in the verified code, a DoS in the unverified archive parser, and a heap buffer overflow in the Lean runtime itself (lean_io_prim_handle_read, lean4#13388). Fixed the same day (PR #13392) and shipped in Lean 4.28.1. Moral: verification moves the trust boundary; it doesn't remove it.

Hex

Verified computer algebra in Lean, against the verified state of the art in Isabelle.

  • 53× faster verified lattice reduction, worst case

  • 7× faster verified lattice-based factoring

  • 15% faster verified classical factoring

  • 1st formally verified van Hoeij factorizer

Not yet competitive with unverified C: about 5× FLINT on factoring, and 5–12× nauty on graph isomorphism.

Sources: Kim Morrison's blog (7 July, 10 Aug, 5 Sept, 8 Sept 2026); leanprover/hex-lll PERFORMANCE.md; kim-em/hex-dev reports/bz-vs-isabelle-investigation.md (30 July 2026); the Hex manual (kim-em.github.io/hex-dev).

Against verified Isabelle (the stats):

  • "53×": LLL on the worst-case Ajtai family at d = 36. Hex's certified path takes 97 ms; Isabelle's verified native reducer takes 5,167 ms. Across the other five lattice families it's 2.6–15× (q-ary 24 vs 82 ms, knapsack 10 vs 26 ms, NTRU 133 vs 1,444 ms, harsh-cubic 59 vs 909 ms, random-bounded 936 vs 7,108 ms). Like for like: this is the fastest verified option each system has. Hex's own exact reducer is only at parity with or slightly ahead of Isabelle's (4,805 vs 5,167 ms on Ajtai).

  • "7×": the lattice-based factorizer against Isabelle's verified LLL factorizer, median ratio 0.137× over 230 eligible polynomials (Hex faster on 182, Isabelle on 48). Hex's lattice route solves 369 of 392 test polynomials; Isabelle's solves 314.

  • "15%": the public classical (Berlekamp–Zassenhaus) factorizer against Isabelle's verified BZ, median ratio 0.852× over 234 polynomials. It's an aggregate lead, not uniform: Isabelle still wins on 91 of them, and on the Chebyshev (1.26×) and Legendre (1.25×) families.

  • These factoring numbers are from 30 July; the August release may be faster again.

What Hex is: a computational algebra library for Lean, built by "spec-driven development". Humans write the specification first; AIs implement both the executable code and its proofs. The computational libraries are Mathlib-free, and separate *Theory libraries connect them to Mathlib. No native_decide; everything is kernel-checkable. Released so far:

  • July: dense matrices, row reduction, Gram–Schmidt, LLL lattice basis reduction.

  • August: integer polynomial factorization (Berlekamp, Hensel lifting, Berlekamp–Zassenhaus, van Hoeij), with irreducibility and factoring tactics.

  • September: certified graph isomorphism (a re-implementation of nauty's dense mode, with a graph_iso tactic), then exact algebraic numbers and number fields.

  • October: fast dense polynomials (Karatsuba, fast division, half-gcd, multipoint evaluation).

Against unverified C/C++ (the muted line):

  • LLL: Hex's certified path is fpLLL's answer checked by a verified Lean checker, so it inherits fpLLL's speed. Ajtai d = 36: 97 vs 73 ms (1.3×). On the other families: q-ary 2.4×, knapsack 2.5×, NTRU 1.2×, random-bounded 2.8×, harsh-cubic 12.6× (59 vs 4.7 ms). PERFORMANCE.md's prose says "1.2–2.5× everywhere", but its own table contradicts that, so don't quote it.

  • Factorization: same asymptotics as FLINT, NTL and PARI, at about 5× FLINT. Van Hoeij has never been formally verified before.

  • Graph isomorphism: 5–12× slower than nauty; the kernel-replayed non-isomorphism tactic is ~5000× slower again. Kim: "nauty is fast!"

The chart is a cactus plot: instances solved (x) against cumulative time (y, log scale), so lower and further right is better. Hex (blue) sits between verified Isabelle (orange, olive) and the unverified C libraries (FLINT, NTL, PARI).

Framing: Hex beats the previous best verified libraries, often by a lot, but it doesn't beat C yet. The certify-a-fast-answer architecture is the trick behind the LLL numbers: it gets you proofs at nearly floating-point speed.

CompPoly

Verified field and polynomial arithmetic for zero-knowledge proofs, against the Rust libraries they're used in.

  • 0.74× Plonky3's time for a proved million-point NTT

  • 1.07× Plonky3's latency for KoalaBear multiplication

  • 0.93× Plonky3's time for the STARK commit step

  • 0 sorrys across 12,489 declarations

At the start of October, CompPoly's NTT took 15× as long as Plonky3's. Every number here comes with a correctness proof.

Sources: CompPoly PRs, Sept–Oct 2026. Most are still open and stacked: #390 (fields vs Rust) → #395 (NTT) → #398 (evaluation), #399 (quartic extension) → #401 (coset LDE) → #402 (quintic extension). #389 (secp256k1) and #392 (Goldilocks) are merged; #391 (four-limb Montgomery) is open. Machine: AMD Ryzen 7 3700X, Lean 4.34.0, Rust nightly with target-cpu=native on both sides.

How to read the chart: Lean time divided by Rust time. Below 1 (indigo) means Lean wins.

Field arithmetic, one core, latency of dependent multiplication chains (#390):

  • KoalaBear 3.41 vs 3.19 ns (1.07×); Mersenne31 1.87 vs 1.75 ns (1.07×); Goldilocks 3.14 vs 2.45 ns (1.28×); all vs Plonky3.

  • BN254 scalar vs arkworks: 20.7 vs 17.9 ns (1.16×), after a 40% speedup in the same PR.

  • Binary towers vs Binius: Lean wins at 64-bit (0.56×) and 128-bit (0.68×), loses at 8-bit (1.71×).

  • Small-field inversion takes 37–66% of Rust's time. Pure Lean: no externs, no compiler changes.

NTT, KoalaBear, 2^20 points, vs Plonky3's parallel AVX2 NTT (#395):

  • 1 worker 7.4 vs 9.2 ms (0.80–0.86×); 4 workers 1.13–1.17×; 8 workers 2.35 vs 3.27 ms (0.72–0.76×).

  • Proved equal to the NTT spec for every input, parallel or not. Trusted base: two ByteArray word accessors, a backport of lean4#14053.

  • The fully extern-free plan is slower: ~4× Plonky3's time on 1 or 4 workers, 2.2–2.4× on 8.

  • "15× as long": on 1 Oct the pre-PR sequential Lean NTT took 49.7 ms against Plonky3's 3.3 ms on 16 threads (comment on #395). It's sequential versus parallel, so say "took 15× as long", not "was 15× slower per core". The same comment had the proved packed version still at 3.5×; it got under 1× later in October.

Coset LDE, the main cost of a STARK commitment (#401): 2^18 × 64 in 81.9 vs 88.2 ms (0.93×), and roughly parity on mid-size and large matrices (0.93–1.24×). Small matrices lose to task overhead (1.7×). On one thread, Plonky3's hand-written AVX2 is 2–3× faster per element; Lean makes it up with parallelism.

Evaluation of one polynomial at one point, 8 workers vs ark-poly (#398): Goldilocks 0.70×, KoalaBear 0.94×, BN254 1.21×. arkworks has no native KoalaBear or Goldilocks, so those rows use its generic Montgomery backend.

Who: the benchmark and polynomial PRs are from mitschabaude-bot ("Gregor's Bots"); the secp256k1, Montgomery and Goldilocks PRs are from Georgios Raikos. The "0 sorry / 12,489 declarations" figure is from #395's axiom sweep.

Gaps

The proofs held up. Here's what these projects still had to work around.

  • Low-level control. Core lacks fast packed-word access, so CompPoly backports it in C. No SIMD types.

  • Per-core speed. Hand-tuned C and Rust still win on one core.

  • A young runtime. Lean-Zip found a bug in Lean's own runtime.

  • Ecosystem. Async and HTTP just landed. No TLS, few libraries, hand-written C bindings.

  • Stability. Monthly releases, breaking changes, no LTS.

Purpose: the last three slides say "verified Lean can match C and Rust". This is the honest caveat, and every gap is one the case studies actually hit.

  • Low-level control: CompPoly's fast NTT relies on two C functions for reading and writing 32-bit words in a ByteArray. Core Lean doesn't have them yet; lean4#14053 proposes adding them, and CompPoly's are a backport. It's tiny: 774 bytes of C, with byte-level Lean definitions that the proofs use and a test checks the C against. They're the trusted base of an otherwise kernel-proved NTT. Without them, the extern-free NTT takes ~4× Plonky3's time (2.2–2.4× on 8 workers). The field arithmetic (#390) uses no externs at all. The vector kernels are plain Lean loops that clang happens to compile to AVX2; there's no way to ask for SIMD directly.

  • Per-core speed: on one thread, Plonky3's hand-written AVX2 is 2–3× faster per element than CompPoly's coset LDE (#401). Hex is about 5× FLINT on factoring and 5–12× nauty on graph isomorphism. Say it out loud: Lean caught up with parallelism (CompPoly) and better algorithms or architecture, such as certifying a fast unverified answer (Hex with fpLLL).

  • Young runtime: Lean-Zip turned up lean4#13388, fixed in #13392 and shipped in 4.28.1. It's a good sign that it was found and fixed quickly, but it's a sign of maturity too.

  • Ecosystem: Std.Async, Std.Net and an HTTP server (Std.Http) are in core as of the 4.3x releases, but there's no TLS in the standard library, few database or cloud clients, and FFI means writing @[extern] C shims by hand. No source-level debugger for compiled Lean either.

  • Stability: a new toolchain roughly every month, often with breaking changes. Projects pin a toolchain and port forward; there's no long-term-support release.

Suggested line: "None of this is fundamental. It's engineering, and a lot of it is exactly the kind of engineering agents are getting good at." That leads into Autoresearch.

Autoresearch

Autoresearch

Give an agent a cost to minimise and a proof it must keep. Then let it loop, overnight.

  • cost ↓ what the agent minimises: time, cycles, code size

  • ⊢ spec what it can never break: the proof must still check

The main idea: a proof is the clearest goal you can give an agent. It can't game the score, so the only way to win is better code that's still correct.

What autoresearch is: Andrej Karpathy's autoresearch (March 2026, github.com/karpathy/autoresearch). An agent edits one file (train.py), trains for a fixed 5 minutes, checks whether validation loss improved, keeps or discards the change, and repeats overnight. The human doesn't edit the code; they edit the instructions (program.md).

What Lean adds: one gate in the loop. Before a change is even benchmarked, Lean has to accept the proof that the code still meets its spec. If it doesn't, the change is thrown away.

Walk the diagram clockwise:

  1. The agent changes the code, however it likes: new algorithm, new data layout, unrolled loops.

  2. Lean checks the proof. This is the constraint, the indigo box. A failed proof sends the agent straight back (the dashed arrow).

  3. Only correct code gets measured against the cost function.

  4. Keep it if it's cheaper than the best so far; otherwise revert and try again.

The cost function is whatever you want: wall-clock time (Lean-Zip, CompPoly), cycle counts (zkVM proving), code size, gas. It's formally "minimise cost(p) subject to ⊢ spec(p)".

Why it matters: an unconstrained optimiser will happily game its metric (Goodhart's law). Return a constant, skip the hard case, overfit the benchmark. With a machine-checked spec, every trick that breaks correctness is rejected automatically, and no human has to review each attempt. That's why it can run unattended, and why the earlier case studies could be optimised by agents at all.

Transition: the competitions that follow are exactly this setup, a fixed spec and a public cost.

better.codes

Prove that a hash-based proof system stays secure with fewer queries. The live companion to the Ethereum Foundation's $1M Proximity Prize.

  • +4.15 bits past the best soundness bound in the literature

  • 81 records, each accepted by Lean's kernel

  • 22 solvers, working with AI agents

  • 6 weeks from first submission to current record

This isn't faster code; it's new mathematics. A better bound means fewer queries, so smaller and cheaper zero-knowledge proofs.

Source: better.codes ("The Proximity Prize", by the Ethereum Foundation, Yukon and zkSecurity), read 28 Oct 2026.

The problem, for a general audience: modern zero-knowledge proof systems (STARKs, zkVMs) rest on properties of Reed–Solomon codes, "proximity gaps", that nobody fully understands. The Ethereum Foundation's Proximity Prize (proximityprize.org; judges Dan Boneh, Giacomo Fenzi and Gal Arnon) offers $1M for resolving the open conjectures. better.codes is the live companion: a toy protocol from Arnon–Boneh–Fenzi 2026 (Construction 6.9), at a pinned parameter point (KoalaBear field, n = 2^18, 128 repetitions). Solvers submit Lean proofs of a lower bound ("Soundness") or an upper bound ("Attack"). Higher proven soundness means fewer queries, which means smaller proofs.

The numbers (KoalaBear track):

  • The literature baseline interval was 64.00 to 116.49 bits. Proved soundness is now 68.15 bits; the attack ceiling is 116.13. The site reports the gap narrowed by 8.6%.

  • First submission 20 Aug at 53.12 bits (below the literature). recmo's +10.45-bit jump on 21 Aug took it to 63.58; it crossed the published bound on 27 Aug, and the current record is 1 Oct.

  • 81 promoted submissions from 22 solvers. Models listed include Claude Opus, GPT-5.6 Sol, GPT-6 Astra and Claude Fable.

  • Every ranked claim is exported, compared against the pinned statement, and accepted by the Lean kernel.

Why it's the clearest "Lean as a constraint" story: the score is a theorem. There's no benchmark to game.

zk.golf

Build the smallest zero-knowledge circuit for a task, proved in Lean to match its spec.

  • 7.4× smaller secp256k1 circuit than circom-ecdsa

  • 2.6× smaller RSA check than zk-email's

  • 1.9× smaller SHA-256 than xJsnark's

  • 0 under-constrained circuits: each one is proved

A smaller circuit means a cheaper proof. And here, a smaller circuit can't be a broken one.

Source: zk.golf challenge API (zk.golf/api/challenges), read 28 Oct 2026. Run by zkSecurity; challenges at github.com/zksecurity/zk-golf-challenges; circuits are written in Clean, a Lean circuit DSL.

What it is: a zero-knowledge circuit is the arithmetic "program" a prover runs to prove a computation without revealing its inputs. Cost (allocations plus constraints) is roughly proving cost. Each submission must come with a Lean proof that the circuit implements the challenge spec; no native_decide, only permitted axioms.

Record vs best existing circuit (the comparison points zk.golf publishes):

  • secp256k1 fixed-base scalar mul: 25,724 vs circom-ecdsa 190,360 (7.4×).

  • secp256k1 scalar mul: 202,281 vs gnark 1,311,228 (6.5×) and circom-ecdsa 2,790,986 (13.8×).

  • RSA-4096 PKCS#1 v1.5 verification: 292,727 vs zk-email 752,852 (2.6×).

  • SHA-256 (256-byte message): 131,995 vs xJsnark 255,380 (1.9×), circomlib 305,565, zk-email 313,655.

  • Keccak-f 1600: 168,960 vs vocdoni 307,200 (1.8×).

  • Binary-field (GF2) BLAKE3 and SHA-256 compression: 1.4× smaller than Flock.

  • Against zk.golf's own baselines: BLS12-381 G1 scalar mul 25.2M → 565K (45×); secp256k1 16.5M → 202K (81×).

Caveats: costs are in zk.golf's cost model, and the comparisons are zk.golf's (gnark's is "R1CS, no lookups"; Flock's are "interface-normalized"). Different proof systems price things differently, so treat these as indicative rather than exact.

"0 under-constrained": under-constrained circuits, where the constraints accept wrong answers, are the most common class of real ZK bugs. A Lean proof against the spec rules them out.

sig.golf

Shrink post-quantum signatures for Ethereum, with security and verification cost proved in Lean.

  • −51% signature bytes × verification cycles, in four weeks

  • −39% verification cycles: 11,573 to 7,007

  • −19% signature size: 6,404 to 5,195 bytes

  • 313 records, each with a new Lean proof

Each record is proved in Lean to keep 127-bit security and to stay within its RISC-V cycle bound.

Source: sig.golf (Yukon, with the Ethereum Foundation; harness Layr-Labs/sig.golf), read 28 Oct 2026.

What it is: Ethereum needs signatures that survive quantum computers. Stateless hash-based signatures (SPHINCS+-style) are the conservative choice, but they're big and slow to verify. sig.golf's score is "spacetime": signature bytes × RISC-V verification cycles. Lower is better.

The numbers:

  • Baseline (30 Sep): 6,404 bytes × 11,573 cycles = 74.1M.

  • Best spacetime now: 5,195 bytes × 7,007 cycles = 36.4M (Rob1Ham, DeepSeek-V4, 27 Oct). The site reports 50.88% leaner.

  • Size record 5,195 bytes; cycles record 6,963 (Th0rgal, at 5,239 bytes).

  • 313 promoted results, every one advancing the size/cycles frontier.

What Lean checks, per the site: that each scheme works, has 127-bit security, and stays within its declared cycle bound. Submissions cite the SPHINCS+ security literature (e.g. Hülsing–Kudinov) and replace FORS with PORS plus forced pruning, among many smaller tricks.

precompile.fast

Replace two of Ethereum's built-in functions with ordinary EVM code, proved correct for every input.

  • 3,600× less gas for MODEXP than the reference EVM code

  • 31× less gas for the RIPEMD‑160 hash

  • 773 Lean-checked records across both tracks

  • 8 weeks since the first submission

A cheaper version only counts if Lean proves it returns the right answer for every valid input, checked against the exact bytecode.

Source: precompile.fast (Yukon, with powdr; harness Layr-Labs/eip8200-challenges), read 28 Oct 2026.

What it is: Ethereum clients run a few built-in functions, "precompiles", as native code. EIP-8200 proposes replacing some with ordinary EVM code, so clients have less special code to maintain. That only works if the EVM code is cheap. MODEXP is modular exponentiation (RSA-style arithmetic); RIPEMD-160 is a hash function.

The numbers:

  • MODEXP: the reference EVM version uses 1,313,215,999 gas over 44 public test inputs; the record is 365.72K gas (i34-9, Opus 5.5, 28 Oct). That's 99.97% cheaper, about 3,590×. 242 promoted submissions from 30 solvers, first on 5 Sep.

  • RIPEMD-160: the record is 618.53K gas (aerugo-ef, GPT-6 Astra, 28 Oct), 96.8% cheaper than its reference, about 31×. 531 promoted submissions from 32 solvers.

  • "773" is 242 + 531 records; solvers overlap between the tracks, so don't add those up.

What Lean checks: Solution.lean must prove the theorem "Correct bytecode": the code returns the right answer for every valid input. Comparator checks the theorem is about the exact submitted bytes and rechecks the proof with a separately built kernel. No sorry, native_decide or extra axioms.

Caveat: "3,600×" is against the challenge's own reference implementation (1,284 bytes of EVM code). I haven't checked how optimised that reference is, so don't claim 3,600× over the best existing EVM MODEXP. Say "than the reference".

LLMs as Compilers

LLMs as Compilers

The usual pipeline: write high-level code, then trust the compiler to get the machine code right.

The new pipeline: give an agent a spec of the program and a spec of the machine, and have it write the machine code directly.

Lean checks the result: the code is proved against the spec, so there's no compiler left to trust.

The idea: a compiler is a trusted translator from source to machine code. Here the agent does the translation, and a Lean proof replaces the trust. You never have to trust the agent, because Lean checks its output.

Why it matters for Ethereum: a zkVM proof covers the execution trace, not the compiler that produced the program. If the guest is written in Rust, rustc and LLVM are in the trusted base. Write the guest in proved assembly and they drop out.

Roadmap for this section:

  • evm-asm: the big version, a whole EVM.

  • xmss-verify-asm: the same method on a small target, done in one sitting, which became the RISC-V track of ots.golf.

  • flapjack: what we learned at scale. Hand-writing everything doesn't scale, so we went back to a compiler, but a verified one.

evm-asm

Agent-written RISC-V, proved against the EVM spec.

Every solid layer is a Lean theorem; checking a whole block is still being proved.

The idea, bottom to top:

  • Bottom: the official Sail model of RISC-V, exported to Lean (the riscv-zkvm package, RV64IM). That's the trust anchor.

  • evm-asm's own RISC-V instruction semantics are proved equivalent to Sail (EvmAsm/Rv64/SailEquiv/), so "is this really RISC-V?" is a theorem rather than a hope.

  • On top, separation logic and Hoare triples with a step bound: cpsTripleWithin N. The bound N is a worst-case cycle count, which matters for zkVM cycle limits and for pricing gas.

  • EVM opcodes: a 256-bit word is four 64-bit limbs. The example on the slide is the real AND: 17 instructions, proved to compute a &&& b on BitVec 256 in at most 17 steps.

  • Top: the stateless guest, which takes a block plus a witness and outputs the post-state root. Its spec, SpecRef, is a Lean port of the Python execution-specs. This top layer is dashed because it's tested but not yet proved.

Why bother: a zkVM proof covers the execution trace, not the compiler that produced the code. If you write the guest in Rust, rustc and LLVM are in the trusted base. evm-asm removes the compiler from the trust story completely. The lineage is Kennedy et al., "Coq: The world's best macro assembler?" (PPDP 2013).

History:

  • Yoichi Hirai started it on 6 Feb 2026. The first real commit was co-authored by Claude.

  • It was slow at first (96 commits in February, 230 in March), then the agents took over: 4,070 commits in April and 19,126 in May.

  • The opcodes came first, then codegen (the Lean Program is emitted as assembly and run on the ZisK emulator), then a whole stateless guest.

Where it got to (dashboard snapshot, 4 Sep 2026):

  • 68 of 85 opcode entries are proved, 3 are conditional, and 14 have only an executable spec. The 14 are the stateful ones: SLOAD/SSTORE, CALL family, CREATE, LOG, KECCAK256. The PUSH/DUP/SWAP/LOG families count once each.

  • The emitted guest passed the Ethereum test suite except 27 failures and 6 errors out of 25,687 fixtures (PLAN.md, July). That's testing, not proof.

  • 2 of the 10 top-level obligations for the north-star theorem (run_stateless_guest_spec) are done.

  • The core has 0 sorry and 0 extra axioms, enforced by CI. The guest-level codegen helpers are unproved scaffolding.

Tease: evm.fast, the autoresearch challenge on making an EVM fast, with the proof as the gate.

xmss-verify-asm → ots.golf

The same method, at small scale: an XMSS verifier, proved in one sitting.

  • 9 h from first commit to the full proof

  • 179 RISC-V instructions, proved for any hash function

  • −34% cycles the next day, from autoresearch

  • 670× fewer cycles on ots.golf in 10 days: 229,113 → 341

The next day, its machine design became the basis of ots.golf's RISC-V track.

Your story: the phone call with Pierre and Justin.

The one-shot afternoon (all times from the git log, BST):

  • 14:38 on 17 Sep: first commit. The goal was "in the style of evm-asm", an RV64IM implementation of the XMSS verifier, proved against the leanVM team's Lean spec (XmssSecurity.Concrete.verify, imported verbatim).

  • 17:17: machine contract, verifier program and test harness. 18:23: the chain walk proved. 19:14: init, the 42-chain loop and the leaf. 20:06: decode. 23:17: the 32-level authentication path and the final compare.

  • 23:29: the end-to-end theorem xmss_verify_correct, merged at 23:40 from a branch literally called one-shot.

What the theorem says: for every hash oracle H, starting from memory that represents (pk, epoch, msg, sig), the 179-instruction program halts with a0 equal to the spec's verify result, and writes nothing outside its scratch area. It uses only the standard axioms (propext, Classical.choice, Quot.sound). The proof is six region contracts composed together. Even the step count is a theorem: the authentication path takes 1090 + 3·popcount(epoch) steps. Separately, 104 end-to-end fixtures and 243 component cases pass in an interpreter.

Caveat: the hash is an abstract oracle reached through one ECALL. leanVM uses BLAKE2s, but implementing it in RISC-V was explicitly out of scope. The project is about 4,100 lines of Lean with about 270 theorems.

The next day (18 Sep), I wrapped it in an autoresearch harness: a statement pin, a committed baseline, and one accept command, plus AUTORESEARCH.md as the agent's prompt. The one-time-signature part went from 3,231 to 2,139 steps (−34%), and the full worst-case verification from 4,427 to 3,335. Every record is in bench/baseline.txt.

ots.golf (leanEthereum; the core repo was created on 16 Sep): "how cheaply can a hash-based one-time signature be verified?" It has five tracks. The RISC-V track runs on the same riscv-zkvm semantics, and its machine file says: "The oracle boundary and counted execution follow Derek Sorensen's xmss-verify-asm design." The cycle count, all on ots.golf's own RISC-V verifier task:

  • 18 Sep, 15:26: the first certified RISC-V root, at 229,113 cycles (Tom Wambsgans, co-authored by me).

  • 18 Sep, 18:24: 24,053. 19 Sep, 01:13: 1,632. 19 Sep, 07:52: 1,628. These were the maintainers' seed roots.

  • 19 Sep, 19:22: the first competitor record, 702 (PR #5). That's under 1,000 within two days.

  • 28 Sep: 341 (PR #64). 229,113 / 341 ≈ 670×. From the first competitor record alone it's about 2×.

  • There were 68 records across all five tracks.

Caveat: the contract changed along the way, for example to a 128-bit nonce and a smaller signature budget, so the 670× spans contract revisions. Each number was checked by the official verifier at its own contract.

Don't compare the 341 with xmss-verify-asm's 2,139: ots.golf lets you design your own OTS scheme (with 127-bit security proved in Lean), so it's a different problem. Its own attribution note says as much.

The site (ots.golf) currently returns 502, so the title links to the GitHub repo.

evm-asm → flapjack

At EVM scale, we stopped hand-writing assembly and ported a verified compiler to Lean.

evm-asm: verified assembly, Feb–Sep

  • 42,676 commits

  • 1.25M lines of Lean

  • 29k theorems

  • 68/85 EVM opcodes proved

flapjack: verified compiler, 8 weeks

  • 27,900 commits

  • 1.08M lines of Lean

  • 24k theorems

  • 100% of 33,614 Ethereum tests passed

flapjack is CakeML's verified Pancake compiler, ported to Lean. The guest is now written in Pancake instead of assembly.

The story:

  • On 2 Sep 2026, Yoichi started stateless-pancaketh: the same stateless guest, written in Pancake instead of assembly. Pancake is a low-level language from the CakeML project, with a compiler verified in HOL4.

  • On 4 Sep, flapjack started: a Lean port of that compiler. The same day, evm-asm's README changed to "project direction is under reconsideration", and its main branch stopped there. It's merged PR #13263, so roughly 9,500 merged PRs in seven months.

  • In 8 weeks flapjack reached about 27,900 commits and about 1.08M lines of Lean.

Where flapjack is now:

  • The Pancake-to-RISC-V correctness theorem is proved in Lean, under explicit assumptions. It's a port of CakeML's pan_to_target theorem.

  • On the 30-fixture baseline, flapjack's output is identical, instruction for instruction, to the original HOL-verified cake compiler: same bytes and same step counts.

  • The flapjack-compiled guest passes the whole tests-zkevm@v21.0.1 corpus: 33,614 of 33,614 records, under both Spike and ziskemu. It also reproduced a real glamsterdam-devnet-7 block (65.3M gas) byte for byte.

  • Backends for MIPS32 (Ziren) and ARMv8 are experimental.

What's not done (be honest on stage):

  • The compiler theorem is about flapjack's own L3-derived RISC-V model, not about Sail. A separate repo proves the two models run in lockstep, but only on the 37 instructions flapjack emits, and only under restrictions. The theorem hasn't been carried over to Sail yet.

  • The Pancake guest itself isn't yet proved against the spec. The README says "no meaningful proof of correctness anywhere in this project yet". Today we have a verified compiler plus a guest that's tested, not proved.

  • flapjack's README says the theorem "might not mean anything" until someone examines it carefully.

Agents: most evm-asm commits carry agent co-author trailers, mainly Claude Sonnet and Opus and OpenAI Codex. Yoichi has about 41k commits under his two identities, and Derek about 1.4k.

Counts are from my local clones: git rev-list --count, Lean line counts, and theorem/lemma declarations, so the theorem counts are approximate. flapjack's commit count is from the GitHub API on 28 Oct.
